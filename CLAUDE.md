# CLAUDE.md

## Purpose
This document contains the project's permanent development and UI guidelines. Before starting any task, always read and follow these instructions.

## General Rules
- Always understand the existing project structure before making changes.
- Reuse existing components whenever possible instead of creating duplicates.
- Follow the project's coding style and architecture.
- Do not modify unrelated files.
- Keep the code clean, maintainable, and production-ready.
- Avoid introducing TypeScript, ESLint, or build warnings.
- Ensure responsive behavior across desktop, tablet, and mobile devices.

## UI & Design Rules
- Always match the project's existing design system.
- Maintain consistent spacing, typography, border radius, shadows, colors, and animations.
- Do not redesign existing UI unless explicitly requested.
- Keep layouts visually balanced and modern.
- Prioritize clean, premium, and user-friendly interfaces.
- Maintain accessibility and proper contrast.

## Reference UI
Whenever I provide screenshots, Figma designs, Dribbble links, or website references:
- Treat them as the primary design reference.
- Match the layout, spacing, alignment, visual hierarchy, and interaction style as closely as possible.
- Adapt the reference to fit the existing project theme rather than copying it exactly.
- If multiple references are provided, combine the best parts while maintaining consistency.

## Development Standards
- Write reusable and modular code.
- Avoid unnecessary re-renders.
- Optimize performance whenever possible.
- Keep components small and maintainable.
- Follow best practices for the framework being used.

## Established Patterns
- **Loose stone listing pages** (`/diamonds`, `/gemstone`, and their `[filter]`/`[type]` variants — `StoneListingClient`): filters live in a horizontal `StoneFilterBar` above the results on desktop/tablet (`lg:` and up), with its own Hide/Show toggle, and in a slide-in `StoneFilterDrawer` on mobile. Both read the same `buildStoneFacets()` output, so any new facet type needs rendering support in both places. Results support a grid/list view toggle (`StoneGrid`'s `view` prop) backed by `StoneCard` (grid) and `StoneListRow` (list) — reuse this pair rather than building a new listing layout.
- **MultiSelectDropdown** (`components/ui/MultiSelectDropdown.tsx`): reusable checkbox-in-a-dropdown control styled to match `Listbox`, used for multi-value filters in horizontal filter bars. Reuse it instead of building another dropdown-with-checkboxes.
- **Sale pricing**: `compareAtPrice?: number` (on both `Product` and `StoneListItem`) is the convention for a struck-through original price next to the current price — only renders when set and greater than `price`.
- **Compare was removed from the stone listing pages entirely** (grid card icon, list-row button, and the results-bar tab) per explicit request — `StoneCompareTray`/`StoneQuickView` were deleted as dead code. `useCommerce`'s `compare`/`toggleCompare` still exist and back the separate jewellery `CompareTray`; don't re-add compare UI to `/diamonds` or `/gemstone` without checking first.
- **Facet range sliders**: `rangeFacetConfig()` / `applyRangeChange()` in `lib/stones.ts` map a `StoneFacet` (by `key`: carat/price/length/width/lw) to `RangeSlider` props and back — add new numeric range facets there instead of hand-rolling another `RangeSlider` block in `StoneFilterBar`/`StoneFilterPanelContent`.
- **Home-page marketing popup** (`components/home/MarketingPopup.tsx`, rendered once from `app/(site)/page.tsx` only): deliberately not the generic "photo left, form right" newsletter-popup template — styled as a navy/gold "gift invitation" card (thin white inset border + gold `CornerMarks` brackets, a `Flourish` divider, and a huge `font-display` numeral offer) to look distinct to this brand rather than like every other ecommerce site. Auto-opens once via a `setTimeout` (`SHOW_DELAY_MS`, currently 5s) after mount; dismissing (X, backdrop click, Escape, or "No thanks") writes `localStorage[STORAGE_KEY]` so it never reappears for that browser, checked before the timer is even scheduled. Submitting the email form swaps the same card (via a shared `layout` motion prop, so it resizes smoothly rather than snapping) to a coupon-code payoff state with a dashed-border click-to-copy code box — reuse this reveal-a-code pattern for any future offer popup instead of a plain "Thanks for subscribing" message. Card width and the two-column (numeral-left/form-right) layout only widen from `lg`/`xl`/`2xl` up — deliberately *not* at the default `sm`/`md` steps — because at in-between laptop widths (~1024–1366px) there isn't enough room for the numeral column + divider + an inline email-input-and-button row; below `xl` the form stays in its original stacked single-column shape instead of squeezing. The email `Input` also needs `min-w-0` alongside `flex-1` in that inline row — a bare `<input>` won't shrink past its intrinsic content width in a flex row without it, which is what caused the field to collapse/overlap the button before the fix. If widening this card further, re-check the narrowest width in each breakpoint step (not just 1440/1920) since that's where a two-column reflow squeezes first.
- **Facet icons use real photos, not abstract SVG outlines, where we have them**: `buildStoneFacets()` attaches an optional `thumbnail` per option — a real catalog photo (`representativeImage()`, preferred; diamonds have these, gemstones don't yet) or, failing that, a real diamond render from `public/shapes/*.png` (`SHAPE_ICON_IMAGE`, sourced from the icon pack originally bundled under `public/product/ALR-RN-CR-075/`). The line-art `StoneShapeIcon` SVG is now the last-resort fallback only. Length/Width/L-W ratio filters are derived from `measurementsMm` via `parseStoneDimensions()` and only appear for a category when that data exists (currently diamonds only — gemstone catalog has no measurements yet).
- **Gallery thumbnails activate on hover, not just click** (`StoneGallery`, matching the existing jewellery `ProductGallery` pattern): thumbnail buttons wire `onMouseEnter`/`onFocus` alongside `onClick` to switch the on-stage media, so desktop users don't have to click to preview. Keep `onClick` too for touch devices. No thumbnail/main-stage container in this view should ever get a `rounded-*` class — the gallery (including the video/iframe view) is square-cornered by convention.
- **Stone listing filter bar / sort bar layout**: `StoneFilterBar`'s header row shows `Result (n)` on the left and the Hide/Show Filters toggle on the right (`justify-between`) — pass it a `resultCount` prop. The active-filter chips (`StoneActiveFilterChips`) and its `Clear All` button live inside `StoneSortBar`'s left side now (via `facets`/`filters`/`onFiltersChange` props), not as a separate block in `StoneListingClient` — `StoneSortBar` has no bottom border anymore. `StoneListingClient` no longer renders the category `<h1>`/description text above the filter bar; the breadcrumb is the only heading-level element left on listing pages.
- **Facet rows that can overflow scroll instead of wrapping**: `StoneFilterBar`'s `HorizontalFacetScroller` renders a facet's options as a horizontally-scrollable single row rather than `flex-wrap`-ing to a second line — fade-in `ChevronLeft`/`ChevronRight` arrow buttons (shown only when there's more content in that direction, tracked via scroll-position state) scroll it by a fixed increment, and touch users can swipe it directly. Currently used by both the Shape (`shape-icon`) and Color (`swatch`) facets; wrap any other facet's option row in it too if it grows wide enough to overflow, instead of letting it wrap. Color swatches (and their no-thumbnail placeholder fallback) are square, not `rounded-full` — this project doesn't use rounded corners anywhere, so don't reintroduce circular swatches.
- **`StoneCard` is a bordered, spec-comparison-style card** (`border border-warm-200 bg-white`, `hover:shadow-luxury` + the usual `y: -6` lift) — deliberately distinct from the jewellery `ProductCard`'s borderless/editorial look, since loose-stone shopping is a spec-scanning grid rather than lifestyle imagery. This was matched to a specific reference screenshot the user supplied (a competitor diamond-card layout); square corners, our gold/ink palette, and `font-display` were kept per "adapt the reference, don't copy it" rather than the reference's rounded corners. Layout: lab badge (small white pill with a `BadgeCheck` icon, linking to `labVerifyUrl()` when available) and a "360°" pill (`Rotate3d` icon, shown when `stone.video` exists) stack top-left on the image; the wishlist heart floats top-right, fading in on hover/focus like `ProductCard`'s icons. Below the image there is no "View Details" button — the entire text block below the image is one `Link` to the detail page (in addition to the image itself being a separate `Link`), so the whole card is clickable. Text is two rows, each `justify-between`: headline (truncating) + price/currency on row one, grade subline (truncating) + `Item#` on row two. Keep this row-pair/no-button structure for any future card info changes rather than reintroducing a CTA button or stacking everything centered.
- **Price text is always `font-sans` (Inter), never `font-display` (Playfair)** — `font-display` is reserved for headlines/names (product name, stone headline, section titles); every price display across the app (`ProductCard`, jewellery/stone `BuyBox`, `StoneListRow`, `StoneCard`) intentionally omits `font-display` so prices stay in the body typeface. Don't add it to a price element even when it sits next to a `font-display` headline in the same row.
- **Collapsible sections use `AnimatePresence` + a `height`/`opacity` `motion.div`, not a bare `{visible && (...)}` mount/unmount** — see `StoneFilterBar`'s Hide/Show Filters panel (`id="stone-filter-panel"`, `initial={{height:0,opacity:0}}` → `animate={{height:"auto",opacity:1}}`, `exit` mirrors `initial`, `duration: 0.35` with the site's standard `[0.22,1,0.36,1]` ease). Apply the same treatment to any other show/hide panel instead of an abrupt conditional render. Also note: the toggle control for a disclosure like this should be one full-width `<button>` wrapping the whole header row (with `aria-expanded`/`aria-controls`) so clicking anywhere in the row toggles it — not a small nested button/link that only the label text responds to.
- **Stone photos fall back to an animated placeholder GIF, never a broken-image icon or the old `GemPlaceholder` SVG** (`GemPlaceholder` was deleted — do not recreate it). `StoneMedia` (`components/stones/StoneMedia.tsx`) wraps `next/image`: it shows the real `src` when present, and swaps to `/diamond-animation.gif` both when `src` is falsy and when the real image's `onError` fires (dead CDN link, 403, etc.), re-arming per stone via a render-time `src`-change check (not a `useEffect`, to avoid the `set-state-in-effect` lint rule). `StoneCard`, `StoneGallery` (both thumbnails + main stage), and `StoneListRow` all use it — route any new stone-photo spot through `StoneMedia` too rather than hand-rolling another `image ? <Image/> : <fallback/>` branch.
- **Video links are validated at catalog-build time only where the host gives an honest HTTP status.** `scripts/build-diamond-catalog.mjs`'s `VALIDATABLE_VIDEO_HOSTS` set (`view.gem360.in`, `diamonds360.in`, `workshop.360view.link`) is HEAD-checked (following redirects) and the stone dropped if its video 404s — confirmed by testing multiple known-real IDs against each host before trusting its status codes, not just one. Every other video host (`d360.tech` — the large majority — plus `video.diamonds360.in` and `v360.diamonds`) renders its viewer entirely client-side and returns an identical 200 for a real or made-up ID, so there's no server-side signal to check; `d360.tech`'s own media API also explicitly returns "Automated scraping is blocked on this service" when probed, so don't attempt a headless-browser or scraping-based workaround for it — those hosts are left unvalidated by design, not by oversight. If a stone on one of the unvalidatable hosts turns out to have a dead video (as reported live in the browser), it can only be fixed by adding its host to `VALIDATABLE_VIDEO_HOSTS` after independently confirming that host actually differentiates real/dead IDs by status code (test ≥2 known-real IDs, not just one — a single dead "real" sample can look identical to a client-rendered shell's behavior), or by getting a known-bad stock-number list from the vendor.
- **Account dashboard** (`/account`, `src/components/account/`): the `Header` profile icon (desktop `UserRound` link, shown `sm:` and up) and the "My Account" entry added to `MobileMenu` (for the sub-`sm` breakpoint where that icon is hidden) both route to `/account` instead of `/login` — the dashboard renders fully-populated mock data as if already signed in, since this codebase has no real auth/session, matching how the rest of the site is mock-data-driven. `AccountDashboardClient` is the single stateful orchestrator: it owns all mutable account state (profile, orders, addresses, wishlist, notification prefs, returns) as local `useState` and switches between section components by id inside an `AnimatePresence mode="wait"` fade — never a real route change, so the persistent `ProfileHeader` banner above the nav+content never remounts. To add a section: add its id to `AccountSectionId` (`types/account.ts`), an entry in `ACCOUNT_SECTIONS` (`lib/account.ts` — this one list drives `AccountNav`), a render branch in `AccountDashboardClient`, and mock seed data in `data/account.ts` if needed. Order/wishlist mock entries embed a full denormalized `Product` snapshot (real slug/image/price copied from the catalog at write time), not a bare id resolved via `getProductById` — order history shouldn't shift if the catalog is later regenerated; follow the same approach for any future mock data that references catalog products.
  The dashboard is deliberately trimmed to essentials per explicit request — don't re-add any of the following without checking first, they were removed as dead weight, not oversight: no loyalty/tier system at all (`CustomerProfile` has no `tier`/`loyaltyPoints`, `ProfileHeader` has no membership badge, Overview has no loyalty/points card); Overview has no "Quick Links" grid, just the stat row + Recent Orders; there is no Recently Viewed or Payment Methods section/tab (`AccountSectionId` and `ACCOUNT_SECTIONS` only cover overview/orders/addresses/wishlist/security/notifications/support/returns/settings); `SecuritySection` is Change Password only (no 2FA, no Active Sessions — `LoginSession`/`SessionDevice` types and `getDeviceIcon`/`sessionLabel` were deleted, so it takes no props); `NotificationsSection` is Email only (no SMS/Push — `NotificationPrefs` has only an `email` key); `SettingsSection` is Personal Information only (no Preferences, no Danger Zone).
- **Sidebar-nav-that-collapses-to-a-scroller layout** (`AccountNav`): one component renders both the mobile horizontal-scroll tab strip (`lg:hidden`, bleeds edge-to-edge via negative margins + the existing `no-scrollbar` utility) and the desktop sticky sidebar (`hidden lg:block`) as sibling fragments. The parent wraps them in `lg:grid lg:grid-cols-[16rem_1fr] lg:gap-10` (no `grid` below `lg`, so mobile is normal block flow) rather than flex — a `display:none` sibling doesn't consume a grid track, which is what lets the desktop aside land beside (not above) the content column using only one nav component. The desktop `<nav>` itself is `sticky top-44` — `top-44` (not a smaller value) is intentional so it clears the site's fixed `Header`, which is taller than it looks (utility bar + main row at `lg:`).
  **Do not add `items-start` (or any `align-items` override) to that grid.** We shipped that once and it silently broke the sticky nav — verified with Playwright by walking the CSS spec's entire containing-block checklist (`overflow`/`transform`/`filter`/`contain`/`container-type` on every ancestor up to `<html>`, all clean) before finding the real cause: `items-start` makes `<aside>` shrink-wrap to exactly `<nav>`'s own height, so `<nav>`'s containing block has zero extra height for it to "hold position" within — per spec, `position: sticky` needs its containing block to be *taller* than the sticky element itself, or sticking is a no-op and it renders pixel-identical to `position: static` (computed style still correctly reports `position: sticky`, which is what made this so non-obvious to spot). The default grid `align-items: stretch` (i.e. no override) is what lets `<aside>` stretch to the row's full height — matching `<main>`'s — giving `<nav>` room to actually stick. Reuse this shape (`top-44`, no `items-start`) for any other "sidebar on desktop, scrollable tabs on mobile" page instead of splitting into two components or reintroducing shrink-wrap alignment on the sidebar column.
- **`StatusBadge`** (`components/ui/StatusBadge.tsx`): a light-tint-background + colored-dot pill for status on a plain white card (order status, return status) — distinct from `Badge`, which is a solid-fill tag meant to sit on a photo (New/Bestseller/-20%). Its tones are the one place this project intentionally uses a hue outside ink/navy/gold/warm/red: `success` is emerald (Delivered/Refunded/Approved), added because color-coded statuses need Delivered to read as unambiguously different from Processing, which an all-brand-palette badge set can't do. `info` reuses `navy/10`, `processing` reuses `gold-50`, `danger` reuses the existing `red-500/600` "alert" precedent (see the wishlist heart), `neutral` reuses `warm-100` — so `success`/emerald is the only genuinely new color; don't add further one-off hues without equally strong justification. Status→tone/label/icon mappings are centralized in `lib/account.ts` (`getOrderStatusMeta`, `getReturnStatusMeta`) rather than inlined per component.
- **`Switch`** (`components/ui/Switch.tsx`): the toggle-switch primitive — pill-shaped track (`rounded-full`, matching the `rounded-full` knob) with a spring-animated knob, for any boolean setting. "On" uses `bg-gold-500` to match the site's existing "this is the active/selected choice" convention (selected size chip, selected quality tier, and checked checkboxes already all use gold-500 for the same purpose). Use this instead of hand-rolling another checkbox-styled toggle, and keep the track's `rounded-full` — this is the one control in the app that's intentionally pill-shaped rather than square-cornered.
- **`Modal`** (`components/ui/Modal.tsx`): the dialog primitive (centered panel, `bg-ink/75 backdrop-blur-sm` scrim, Escape-to-close, body-scroll-lock, click-outside-to-close) — factors out the overlay pattern `MarketingPopup` had implemented ad hoc. Any new "add/edit X" form or confirmation prompt should use this rather than reimplementing that logic again.
- **Client-only "download" actions use a real `Blob` + temporary `<a download>`, not `window.print()` or a fake toast** — see `downloadInvoice()` / `buildInvoiceText()` in `lib/account.ts` (the order card's Invoice button). There's no backend to render a PDF from, but a real downloadable `.txt` receipt is honest about what it does; prefer this over simulating an action that doesn't actually produce anything.
- **Dashed-border "add new" affordance**: an inline "add" card among existing item cards uses `border border-dashed border-warm-300` (+ `hover:border-gold-400 hover:text-ink`) rather than the usual solid `border-warm-200`, so it reads as an empty slot rather than existing content — see "Add Address" in the account dashboard. Reuse this treatment for any other inline "add a new X" affordance.
- **Backend API layer mirrors tcctechweb** (`src/framework/basic-rest/**`, `src/utils/encrypt-decrypt-data.ts`): this site talks to the *same* tcctech backend service as the `tcctechweb` repo (different DB), so the integration deliberately copies that project's structure and file naming rather than inventing a new one — `@framework/utils/http` (client), `@framework/utils/api-endpoints` (`API_ENDPOINTS` path constants, keys/paths kept identical to tcctechweb's so the two frontends stay interchangeable), `@framework/<domain>/get-*.ts` (one module per endpoint). Path aliases `@framework/* → src/framework/basic-rest/*` and `@utils/* → src/utils/*` match tcctechweb's `tsconfig`. **The request contract is non-obvious and must be reproduced exactly or the API rejects the call**: `Authorization: <auth token | "PUBLIC_AUTHORIZATION_TOKEN">` with **no `Bearer ` prefix**; an encrypted `company_key` query param (AES-256-CBC hex of `NEXT_PUBLIC_COMPANY_INFO_KEY`) appended to *every* request; and when `NEXT_PUBLIC_SECURE_COMMUNICATION === "true"`, request bodies are encrypted and **the response body comes back as hex ciphertext that must be decrypted then JSON-parsed** (handled centrally in `http.ts`'s `parseBody`, which tolerates both raw and JSON-quoted hex). Env vars use tcctechweb's names verbatim (`NEXT_PUBLIC_REST_API_ENDPOINT` including the `/api/vN` segment, `NEXT_PUBLIC_IMG_URL`, `NEXT_PUBLIC_COMPANY_INFO_KEY`, `NEXT_PUBLIC_ENCRYPT_DECRYPT_KEY`/`_IV`, `NEXT_PUBLIC_SECURE_COMMUNICATION`) — copy them from `tcctechweb/.env.local` and only swap the endpoint host. Values there often carry stray whitespace, so `.trim()` anything read from env. `next.config.ts` derives `images.remotePatterns` from `NEXT_PUBLIC_IMG_URL`/`NEXT_PUBLIC_REST_API_ENDPOINT` instead of duplicating the host.
  Two deliberate deviations from tcctechweb, both because this is an App Router project: **fetch instead of axios** (Server Component calls go through Next's fetch cache via `next: { revalidate }` for ISR — axios bypasses it and would re-hit the API every render), and **no react-query** (data is fetched server-side in `page.tsx`, not in a `useQuery` hook).
- **Jewellery listing pages render live API data with no static fallback** (`/jewellery/[category]` → `getProductsByCategoryFromApi`): the grid comes from `user/product/list` filtered by `product_category`, **not** from `user/product/featured/list` — the featured feed is admin-curated and currently returns `data: []` on this DB, so binding it to the listing would render an empty page. The featured binding still exists (`get-all-featured-products.ts`) for when products are flagged. `JEWELLERY_CATALOG`/`getProductsByCategory` are no longer used by the listing page, but are still live for `/products/[slug]`, `getRelatedProducts`, and category tiles — don't delete them.
- **`product_category` filter values are not this site's slugs** — `CATEGORY_API_SLUG` in `normalise-product.ts` maps them (`rings`→`ring`, `pendants`→`pendant`, `earrings`→`earring`, while `necklaces`/`bracelets` match). A wrong value returns `total_items: 0` with a **200 success**, not an error, so a silently empty category almost always means a bad slug here; check against `user/filter/list/category`.
- **Product image URLs are resolved against the base the API reports, never a hardcoded CDN**: `getImageBaseUrl()` reads `user/companyinfo` → `web_setting.image_base_url` (currently the `forever-jewels-prod` S3 bucket) and caches it per process, exactly as tcctechweb does via `CompanyInfo.web_setting.image_base_url`. `NEXT_PUBLIC_IMG_URL` is only a fallback and a way to tell `next.config.ts` which host to allow in `remotePatterns` (it can't call the API) — the tcctechweb CloudFront hosts 403 on this DB's assets, so don't copy an image host between companies. API `product_images` carry `image_type` 1 = still, 4 = mp4 video, and arrive unordered with `-1`/`-2`/`-model` filename suffixes; `normaliseProduct` sorts by that trailing number so the `-1` packshot becomes the card's primary image.
- **Product detail is API-backed too** (`/products/[slug]` → `getProductDetailBySlug`, `POST user/product/details`): the page no longer reads `getProductBySlug`/`JEWELLERY_CATALOG`, and `generateStaticParams` returns `[]` so detail pages render on demand and cache via ISR rather than prerendering hundreds of API calls per build. Related products come from the category feed and are passed to `ProductDetailClient` via its optional `related` prop — without it the component falls back to `getRelatedProducts()`, which would put static mock products underneath live API data.
- **`user/product/details` needs a PLAIN JSON body, not the encrypted wrapper** — posting `{ data: <hex> }` (what tcctechweb's axios interceptor sends when `NEXT_PUBLIC_SECURE_COMMUNICATION=true`) gets a **200 with `"Product not found!"`**, not an error, so it looks like a bad slug. `http.post` therefore sends plain JSON by default and encryption is opt-in per call via `encryptBody`. This backend also returns plain (unencrypted) JSON responses despite that env flag being `true`.
- **The detail payload is NOT shaped like the list payload** — same backend, different field spellings, and mixing them up yields silently empty values: `PMO`/`PDO` are **uppercase** here (lowercase `pmo`/`pdo` in the list); there is **no `retail_price`** (price is `PMO[0].after_discount_product_price` / `.Price`, formatted strings like `"1,150.00"` that must be parsed); image tone is **`metal_tone_sort_code`** (vs `metal_tone_short_code` in the list); and `category_name` is capitalised (`"Ring"`) vs lower-case in the list — which is why `resolveCategoryFromNames()` takes already-lower-cased names. Tone data is genuinely absent on some products (`metal_tone_sort_code: null`, `metal_tone: []`), so a spec row reading just `14K` with no tone is correct output, not a mapping bug — don't infer the tone from the `-WG-`/`-YG-` filename segment, since two-tone products exist.
- **`ProductSpec.label` must be unique per product** — `ProductAccordions` keys spec rows by `key={spec.label}`, so emitting several rows with the same label (e.g. one `"Stone"` row per `PDO` entry) triggers a React duplicate-key error and can drop rows. `get-product-details.ts` labels them `Centre Stone` / `Side Stone n` for this reason.

- **`next/image` needs `dangerouslyAllowLocalIP` in development for the S3 product photos** (`next.config.ts`): Next's image optimizer resolves every upstream hostname and returns a **400 "url parameter is not allowed"** if *any* resolved address looks private (SSRF protection; logged server-side as `"upstream image" ... "resolved to private ip"`). On NAT64/DNS64 networks the public S3 bucket resolves to `64:ff9b::/96` addresses, which that check flags — so product tiles render blank. The tell is that it's **intermittent**: the same page shows some photos and not others, and a plain `curl` of the S3 object returns 200, because only some DNS answers come back NAT64. Don't chase this as a bad URL, a missing `remotePatterns` entry, or the fact that S3 serves `.webp` as `application/octet-stream` (Next sniffs the bytes, so that content type is fine) — check the dev log for "resolved to private ip" first. The flag is scoped to `process.env.NODE_ENV === "development"` so production keeps the protection; if a deployed host also runs IPv6-only/NAT64, it will need the same treatment there.

- **The API base URL must include the right `/api/vN`** — this backend serves **v4**; v1/v2/v3 return a plain-HTML 404. tcctechweb's `.env.local` points at v1 on a different host, so copying it verbatim yields 404s on every endpoint.

- **Standalone content pages** (`/about`, `/our-story`, `/contact`, `/careers`, `/terms`, `/privacy`): all six share `PageHero` (`components/content/PageHero.tsx`) — navy band, gold eyebrow, `font-display` title, light `Breadcrumb` whose trailing crumb is generated from `title`, and the standard fixed-header clearance (`pt-36 sm:pt-40 lg:pt-52`). Use it for any new marketing/legal page instead of hand-rolling another header. Their copy lives in `src/data/company.ts` (values, story timeline, job openings, benefits, and the `LegalSection[]` documents), not inline in the page components, matching how the rest of the site keeps content in `src/data/`. Long-form legal pages render through `LegalDocument`, which pairs the body with a sticky contents rail reusing the documented `sticky top-44` + **no `items-start`** grid shape — adding an `align-items` override there would shrink-wrap the aside and silently kill the sticky nav, exactly as it did in `AccountNav`.
- **Cart / Wishlist are client-side only today** (`useCommerce` + `/cart`, `/wishlist`): state lives in React context persisted to `localStorage[forever-jewels-commerce]`, **not** on the backend, so it does not follow a user across devices and there is no logged-in sync. `wishlistItems` stores a full `Product` snapshot per saved id — ids alone are no longer enough now that products come from the API and cannot be resolved from a static catalog. Callers that have the product must pass it: `toggleWishlist(product.id, product)`. The backend endpoints for real sync exist (`user/product/variant/wishlist`, `user/all/product/cart/*`, `user/all/product/cart/merge`) and are unbound — binding them requires auth first.
- **PDP purchase flow, not enquiry**: `BuyBox` now uses `Add to Bag` / `Buy Now` wired to `useCommerce`, replacing the WhatsApp "Inquiry Now" CTA, and the "0% APR financing" line is gone. `StoneBuyBox` (loose diamonds/gemstones) **still uses Inquiry Now** — those have no cart flow yet. The PDP's `Description` accordion renders `product.longDescription`, parsed from the API's `long_description` HTML into paragraphs by `htmlToParagraphs()`; it is deliberately stripped rather than passed to `dangerouslySetInnerHTML`, since it is unsanitised backend HTML.
- **Search goes through `/api/search`, not the browser** (`app/api/search/route.ts` → `searchProducts`): the REST API is plain `http` in some environments, which a browser blocks as mixed content from an `https` page, so the typeahead calls a same-origin route handler that queries server-side. Search uses `user/product/list` with `search_text`, **not** the dedicated `user/product/serach/list` endpoint — both return the same matches, but the dedicated one returns `image_path: null` on every row for this DB, leaving every thumbnail blank.
- **SEO files are generated, not static** — `src/app/sitemap.ts` and `src/app/robots.ts` (Next metadata routes). The sitemap pulls live product URLs from the API and revalidates hourly, so new products enter the index without a redeploy; it degrades to the static routes if the API is unreachable rather than failing the build. `robots.ts` blocks `/account`, `/cart`, `/wishlist`, `/checkout`, `/login`, `/signup`, `/api/`; those pages also set `robots: { index: false }` in their own metadata.

- **Education hub** (`/education` + `/education/[slug]`): article content lives in `src/data/education.ts` as `EducationArticle[]` (category, excerpt, readMinutes, intro, and `ContentSection[]` body) — add a guide by appending an entry there, and `generateStaticParams` picks it up automatically. The slugs are not arbitrary: `navigation.ts` and `Footer.tsx` already link to `/education/{diamond-shapes,4cs,gemstone-guide,birthstones,jewellery-care,metal-guide,warranty,conflict-free,resizing,price-match,shipping}`, so **renaming or removing a slug breaks an existing nav link** — grep before changing one.
  **All education copy is originally written.** Competitor education pages (Blue Nile and similar) may be used to check *topic coverage* only — their article text is copyrighted and must never be copied, paraphrased closely, or pasted in. Facts (Mohs values, the 4Cs, karat percentages) are not copyrightable; sentences are.
- **`ContentSections`** (`components/content/ContentSections.tsx`): the shared long-form renderer — sticky contents rail plus `ContentSection[]` body, driven by the `ContentSection` type in `src/types/content.ts`. Both `LegalDocument` (which just adds the "Last updated" line) and the education article template render through it; use it for any new section-based document rather than repeating the layout. Its `meta` prop takes any node for the small line above the body.

- **`ContactForm` has no backend and says so** (`components/content/ContactForm.tsx`): it validates natively (`required`, `type="email"`) and swaps to an inline confirmation state rather than faking a network request or firing a toast that implies delivery — the same honesty principle as `downloadInvoice()`. Wire its `handleSubmit` to a real endpoint when one exists. Note `SocialIcon` takes **no `href`** — wrap it in an `<a>` as the footer does.

- **Diamond inventory data source**: `scripts/build-diamond-catalog.mjs` reads `data-sources/Stock.xlsx` (not the old `LOOSE_DIAMOND_LIST.xlsx`, which is now stale/unused) and regenerates `src/data/diamond-catalog.ts`. This sheet's schema differs from the old export: price comes from a single `rate` column (read as $/carat; total price = `rate * weight`), fancy-colored stones report color via `fancy color`/`color intensity` instead of a `color` grade letter (`colorFor()` in the script merges these, treating GIA-style grade codes that land in the fancy-color column as plain grades), and `growth type` is `CVD`/`HPHT`/blank rather than an explicit natural/lab-grown flag (blank ⇒ natural). Rows are skipped when `rate === 0` (~22% of this export, all from one vendor feed — there's no "price on request" concept in `StoneListItem`, so a $0 stone would just look broken) **or** when either `image` or `video` is missing (catalog only carries fully-photographed/videoed stock, currently 737 of 1945 rows) — re-run the script after dropping a fresh export into `data-sources/`.
